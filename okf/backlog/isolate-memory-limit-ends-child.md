# Make reaching an isolate's memory limit end the child

## Problem

`isolate(id, { memoryLimit })` sets QuickJS's memory limit on the child
runtime. The documented contract is that allocations then fail with an
out-of-memory error where they happen. At the limit that contract does not
hold, and the child becomes unreliable in three ways:

- **A call never settles.** The child's reply is a promise reaction. QuickJS
  enqueues it with `JS_EnqueueJob`, ignores a failed enqueue, and drops the
  reaction. The child's loop stays alive, the link stays open, and the
  parent's call (and its in-flight hold) waits forever.
- **A failure is silent.** The same drop takes an `await` continuation, or
  the rejection handler that reports the entry's failure. A handler was
  attached, so the rejection tracker counts the rejection as handled and
  nothing is logged. `exited` can settle with `null`, which reads as a clean
  end.
- **The message has no cause.** With no room to build its out-of-memory
  error, QuickJS throws `null`. The parent sees
  `module error: Exception generated by quickjs: Null"null"`.

The limit hit during the engine's own startup is fixed (the limit and the
interrupt handler are applied after startup, `init_context` in
`flux/src/plugins/mod.rs`), and the plugins a limited (non-gui) engine
loads no longer panic on a failed allocation. What remains is behaviour
inside QuickJS, which flux cannot repair
call by call. For now the docs state it (`memoryLimit` in
`packages/flux-types/modules/isolate.d.ts`) and tell the app to put a
signal on calls and terminate the child.

## Direction

Make the limit an event flux observes, and make that event fatal to the
child.

QuickJS enforces its own limit silently: it refuses the allocation and tells
nobody. So flux has to be the one that hands out the memory. rquickjs
exposes this (`AsyncRuntime::new_with_alloc`, the `Allocator` trait). The
allocator cannot throw: QuickJS calls it from deep inside its C code, and
its only answers are a pointer or null. What it can do is count and raise a
flag.

1. A counting allocator, used only for an engine with a memory limit. It
   wraps the allocator the engine uses today, counts the live bytes, refuses
   an allocation that would pass the limit (as QuickJS does now), and sets
   an out-of-memory flag when it refuses.
2. The engine reads the flag at its safe points. The interrupt handler
   returns true while it is set, so busy JS unwinds. The run loop checks it
   after each turn and ends. Whatever QuickJS dropped in between does not
   matter, because the child ends anyway.
3. The report is built in Rust, with no JS heap: the uncaught hook receives
   a message such as `Out of memory: the limit of <n> bytes was reached`. In
   the isolate that travels on the link as the exit cause, so pending and
   later calls reject with `isolate '<id>' exited: Out of memory ...` and
   `exited` settles with it.
4. The docs change: reaching the limit ends the child. This is what the
   worker limits of the platforms do.

## Decisions to take

- **Is every refused allocation fatal?** The simple rule is yes: a script
  that asks for more than the limit in one allocation (and would catch the
  error today) ends its child. The alternative lets one oversized request
  fail as a catchable error while the heap is far from the limit, and it
  needs a rule for "far".
- **A reserve beyond the limit.** Granting a small overshoot lets the
  allocation that crosses the line succeed, so no operation fails halfway
  before the engine reaches a safe point. It is a refinement, not a need:
  the child ends in both cases. If it is added, an oversized allocation is
  still refused, or one request defeats the limit.
- **The embedder's `memory_limit`.** `FluxEngineBuilder::memory_limit` gets
  the same behaviour, or the fatal rule is an isolate choice above it. An
  observable goes with it either way (the root `CLAUDE.md` API design
  rule): the exit cause.

## What done looks like

- A child that reaches its limit always ends, and every pending call
  rejects with a message that names the limit.
- `exited` settles with that message, never with `null`.
- No call to a limited child can stay pending because of the limit. The
  test walks the edge of the limit (fill the heap, then release one chunk
  per step and call) and asserts that every call settles.
- The cost of the counting allocator is measured once on a release build.
  It is one add and one compare per allocation, and QuickJS keeps the same
  count today, so the expectation is no visible cost.
