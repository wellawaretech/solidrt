# quickjs-ng: promise reactions are dropped at the memory limit

We did not file this. Others reported it upstream as pull requests, with no
issue beside them. This note tracks them.

## The bug

A runtime at its limit (`JS_SetMemoryLimit`) cannot allocate a job.
`JS_EnqueueJob` then returns -1. Two callers ignore that result, and both
free the reaction data afterwards, so the reaction is gone:

- `fulfill_or_reject_promise`: a pending promise settles and queues the
  reactions of its subscribers (`quickjs.c:55648` in the vendored copy).
- `perform_promise_then`: `then` on a promise that is already settled
  (`quickjs.c:56470`).

The `then` handler or the `await` continuation never runs. The derived
promise stays pending forever. No exception reaches JS or the host.

The enqueues of `js_dynamic_import_job` (`:32002`),
`js_promise_resolve_thenable_job` (`:55816`) and `js_finrec_job`
(`:63387`) ignore the result too.

## Reproduction

An engine with a memory limit a little above its baseline. The script fills
the heap in small chunks until an allocation throws. Then it awaits a timer
promise and logs after the `await`. In a band of limits the log line never
appears, and nothing is reported.

## What it does to us

It only shows in an engine with a memory limit, which is a `flux:isolate`
child with `memoryLimit`: a call to the child can stay pending forever, and
a failure can go unreported. Our answer for now is the documented
limitation on `memoryLimit` (`packages/flux-types/modules/isolate.d.ts`).
The symptoms in full and the fix on our side are in
[isolate-memory-limit-ends-child](../backlog/isolate-memory-limit-ends-child.md).

## Upstream status (2026-11-16)

quickjs-ng, all open, none reviewed or merged:

- [#1870](https://github.com/quickjs-ng/quickjs/pull/1870) "fix: reserve
  Promise reaction jobs before settlement": the `fulfill_or_reject_promise`
  site. It reserves the job when `then` subscribes, so that settling does
  not allocate. This is the one behind the call that never settles.
- [#1867](https://github.com/quickjs-ng/quickjs/pull/1867) "fix: report
  settled Promise subscription enqueue failure": the `perform_promise_then`
  site.
- [#1872](https://github.com/quickjs-ng/quickjs/pull/1872) "fix: propagate
  thenable adoption allocation failures": the thenable job.
- [#1866](https://github.com/quickjs-ng/quickjs/pull/1866) and
  [#1873](https://github.com/quickjs-ng/quickjs/pull/1873): the base and
  the next layer of the same stack.
- [#1808](https://github.com/quickjs-ng/quickjs/pull/1808) touches the
  same call sites for promise hooks and still ignores the failure. It
  conflicts with the stack.

Bellard's QuickJS (github.com/bellard/quickjs) has the same code on its
master and no report. Its mailing list archive was not searched.

rquickjs has no report of lost promises under a memory limit.

## Related upstream behaviour

- [#1810](https://github.com/quickjs-ng/quickjs/pull/1810) "Make OOM
  exceptions uncatchable by JS code" merged on 2026-10-08, after the commit
  we vendor. It arrives with a later rquickjs: a script will not catch an
  out-of-memory error then. That is the rule our backlog item proposes: a
  child cannot catch the error and carry on.
- When the out-of-memory error itself cannot be built, `JS_ThrowError2`
  throws `null`. That was reported as
  [#798](https://github.com/quickjs-ng/quickjs/issues/798) and closed as
  expected behaviour. Our messages show it as
  `Exception generated by quickjs: Null"null"`.

## What to do

- Do not open a new quickjs-ng issue: it duplicates #1870 and #1867.
- On every rquickjs bump, check whether #1870 and #1867 are in the vendored
  quickjs-ng. When they are, set this note to `resolved`, re-run the
  memory-limit tests, and revisit the limitation in `isolate.d.ts` and the
  backlog item.
