# okf

Working notes. The directory a document sits in **is** its state - there is no
`status:` field, because two sources of truth means the field wins and the
directory rots. Things change state by `git mv`.

```
ideas.md      one line per idea. no ceremony.
backlog/      shaped, not started
plans/        decided and being worked on now
done/         finished, kept
notes/        knowledge - no lifecycle, no state
upstream/     bugs in our dependencies; draft report plus upstream status
index.md      generated by scripts/build-okf-index.ts. never hand-edited.
```

## The states

**ideas.md** - one line, no file, no frontmatter. If capturing an idea costs a
formatted document you stop capturing ideas. An idea that gets shaped graduates
to a file in `backlog/`, and the line stays behind with a link so the trail
survives.

**backlog/** - shaped means you can state the problem, what done looks like,
and roughly what it involves. Agreement that something should happen is backlog,
not a plan.

**plans/** - decided and being worked on now. Not capped, but the rule that
keeps this folder honest is: a plan nobody is working on goes back to
`backlog/`. Without that move `plans/` silently becomes a second backlog and
the directories stop meaning anything. The generated index shows the count, so
growth is at least visible.

**done/** - finished plans and backlog items, kept for their reasoning. Never
re-read unless asked. Growth here is free; growth in `plans/` is not.

**notes/** - knowledge, which has no lifecycle. It is not in progress or done,
it is true or it is wrong. Codebase assessments, design surveys, measurements,
decisions and the evidence behind them.

## Finishing a plan

Two moves, no writing:

1. `git mv plans/x.md done/x.md`
2. Cut its `## Findings` section into `notes/`, leaving a link behind.

The section is appended to **during** the work, when you have just found the
thing and are motivated to write it down. That is the whole trick - distilling
at the end fails because the end is the moment of least motivation. If there is
nothing to author at completion, completion happens.

What gets cut, and what stays: **would this still be true if the plan had never
existed?** "Impeller inverts sampled textures on the ANGLE path" is true either
way - that is a note. "We did the raster thread before the frame driver" is
plan archaeology - that stays in `done/`.

A done item carries no open work. Anything still actionable when you close
something goes back to `backlog/` as its own item, written symptom-first, and
the done file only links it. Deliberate non-goals - things not done on purpose -
may stay in the done record.

## Where knowledge actually lives

`notes/` is not the first choice. If a finding fits next to the thing it
governs, it belongs there: a Rust doc comment on the function that carries the
trap, `packages/*/AGENTS.md` for the rules an app author needs, the root
`CLAUDE.md` for conventions that bind every file. A second copy in `notes/`
would drift from the code it describes, and the stale one is the one you would
read.

`notes/` takes what is too narrow for a doc comment and too large for one -
typically the measurements underneath a claim the code states in one line, or
knowledge that spans crates and so has no single home.

## Bugs

Not a category. A bug is work: `backlog/` if it should be fixed, `plans/` if it
is being fixed now. A `bugs/` directory duplicates the entire lifecycle and you
maintain two of everything.

One exception worth knowing: a bug you have decided **not** to fix has stopped
being work and become a documented limitation. That goes to `notes/`. Otherwise
it sits in the backlog forever making the backlog a fiction.

## upstream/

Not a state, which is why it is named after what it holds rather than a stage
of work.

Bugs in our dependencies. The write-up doubles as the draft
report, and this is the one place a `status:` field survives, because the state
it tracks is the dependency's, not ours, and no `git mv` of ours can express it.
These files also carry `project:`, `versions:` and `link:`.

```
unfiled          written up here, nothing reported upstream yet
filed            issue opened upstream; link in frontmatter
acknowledged     upstream confirmed the bug
fixed-upstream   fix merged or released upstream, not yet in our tree
resolved         fix arrived in our dependency tree; local workarounds can come out
expected         upstream closed it as working-as-intended; workaround is permanent
wont-fix         upstream declined; workaround is permanent
```

On `resolved`, `expected` or `wont-fix`, note the outcome in the file and update
any code comment that references it.

## Frontmatter

```yaml
---
title: Short imperative phrase
description: One sentence. This is what the generated index shows.
created: 2026-08-13
---
```

That is all of it. `done/` adds `completed:`. `upstream/` adds the four fields
above. No `status`, no `type`, no `timestamp` - the directory says the state and
the filename says the topic.

## The index

`index.md` is generated from that frontmatter by `scripts/build-okf-index.ts`.
A hand-maintained index is a lie with a delay: correct the day it is written,
drifting from the next `git mv` onward.

```
bun scripts/build-okf-index.ts            regenerate
bun scripts/build-okf-index.ts --check    fail if stale or if frontmatter is missing
```
